# 文章写法规范

> 状态：已批准 · 2026-10-29
> 上游：维护者 2026-10-29 的要求（「前面的文章格式和写法太放飞自我，给我一个 example.md」）
> 下游：`src/content/posts/` 的每一篇文章；建稿脚本 `scripts/new-post.mjs` 的模板
> Owner：维护者
> 复核/证据：2026-10-29 对站内 4 篇文章做了一轮统一修订，修订前后 `npm run verify` 均通过；示例见 [example.md](example.md)

## 1. 原则

**结构要能扫读，语气要像你说话。** 两条同时成立才算合格。

- 结构：只读标题就知道文章讲什么；第二遍读不用回头找定义。
- 语气：吐槽、自嘲、emoji 照留，不改成公文腔。

不是把所有文章改成同一副样子，而是让**同一种元素**在所有文章里长得一样：标题层级统一、frontmatter 统一、代码和公式统一，口气各篇各的。

## 2. 建稿与 frontmatter

建稿用 `npm run new -- <文件名>`（或双击「新建文章.bat」）。frontmatter 骨架由脚本生成，**不要手抄**。

标签清单**不要**往 frontmatter 里复制粘贴——清单的唯一来源是 `src/const.ts` 的 `TAG_SHAPE`，复制的那份必然过期（2026-10-29 修订前，站内三篇文章存着三份不同的清单，其中一份还带着改名前的 `Github`）。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 文章标题。目录页、浏览器标签、RSS 都用它 |
| `description` | 是 | 一句话摘要，写"这篇解决了什么"，不是标题的复述 |
| `pubDate` | 是 | `YYYY-MM-DD`。**排序和 RSS 只认它** |
| `pubTime` | 否 | `HH:MM`，24h 零填充。纯显示用，不要就删整行 |
| `updatedDate` | 否 | 只在真改过正文时才写。改了内容却不写，读者看不出文章动过 |
| `tags` | 否 | 从 `TAG_SHAPE` 里选；要用新标签先去那里登记形状，否则徽章回退圆形并告警 |
| `draft` | 否 | `true` = 草稿：不进目录页/标签/RSS，不生成线上页面，`npm run dev` 可预览 |

`pubTime` 是**纯显示字段**，不参与任何日期运算，不要把它并进 `pubDate`（会重新引入时区坑）。

## 3. 正文骨架

推荐结构（不是硬性模板，但每篇至少要有"背景 → 做法 → 结论"这三段）：

```markdown
（可选）吐槽 / 心情引用块
（可选）导语：一两句把话题抛出来

## 背景 / 题目

## 做法 / 思路

## 坑 / 证明 / 复杂度

## 结论

（收尾一句）
```

- **开头先给吐槽或导语**，别一上来就 `##`。
- **结尾留一句收尾**：一句吐槽，或者"下一步打算做什么"。别让文章戛然而止。
- 小节控制在 2~4 个，别把每段话都升成 `##`。

## 4. 标题层级

- `h1` 由 frontmatter 的 `title` 提供。正文里**不要**再写一个与标题同名的一级标题（重复）。
- `##` = 一级小节。站点给 `h2` 加了红色方块标记，是正文里最重的视觉锚点。
- `###` = 二级小节。
- **不用 `h4` / `h5`**：`.prose` 只给 `h2`/`h3` 上了样式，`h4` 及以下会掉回浏览器默认字号，看起来像没写完。
- **不跳级**：不要 `h2 → h5 → h4`。要再细分就把一个 `h2` 拆成两个 `h3`。
- 小节标题写**内容**，不写情绪。「为什么一定有循环」可以；「说啥好呢~」当小节标题不行（它该是导语里的一句吐槽）。

## 5. 元素用法

### 代码块

- **必须标语言**：` ```bash `、` ```cpp `、` ```go `……
- 块里只放能直接跑的命令。要说明"这里得换成你的端口"，写在块外，别塞进块里当注释。
- 长代码按逻辑分段，段间留空行；不要逐行加中文注释解释每一行。

### 行内代码

命令、文件名、字段名、报错信息一律用 `` `反引号` `` 包起来。

### 公式

- 行内 `$f(x)\le81d$`；独立成行用 `$$…$$`，前后各留一个空行。
- **公式里不要塞裸中文**。中文语义用 `\text{…}` 包住，例如 `$f(x)=\text{各位数字的平方和}$`；能用文字说清的，别塞进公式。
- 独立公式太长就拆成多个 `$$` 块——构建期会给公式包一层可横向滚动的容器，拆开读起来更舒服。
- KaTeX 语法错（例如 `\foo`）只会把公式标红、**不挡发布**，所以发布前要自己扫一眼有没有红字。

### 列表

- 并列的点用 `-`；有先后顺序用 `1.`。
- 列表项之间不空行，紧凑排。

### 表格

- 只在真的需要逐行对照时用（配置项对照、复杂度对照）。窄屏下表格会横向滚动，别拿它当排版工具。

### 引用块

- 用途固定：**吐槽、心情、成绩、题记**。写成 `> *斜体*`，跟正文明确区分。
- 一篇最多一两个。多到第三第四个，就不叫重点了。

### 链接

- **不要裸贴 URL**：写 `[LeetCode 202 · 快乐数](https://leetcode.cn/problems/happy-number/description/)`。裸 URL 不可点击，也不好看。
- 站内链接写在 `.astro` 里时走 `src/const.ts` 的 `u()`；文章正文里提到站内页面就直接写文字，不要手拼 `/xin-s-blog/...`。

### 图片

- 图片文件放 `src/content/posts/` 内，正文用相对路径 `![图](./diagram.png)`。
- **不要**用 `/` 开头的根绝对路径——构建不会给它补子路径前缀，部署后会 404。

### 分隔线

`---` 用来切大段落，一篇最多一次。多数情况用 `##` 就够了。

## 6. 中文排版与语气

- 中英文、数字之间留一个空格：`CF Div2 D`、`2200 排名`、`3 位数`。
- 用全角标点：`，。、：；？！（）「」`。
- 破折号写 `——`（两个），不写 `--`。
- 强调用 `***…***`，作用是"拍桌子"。一篇两三处封顶，篇篇都用就没有重点了。
- emoji 可以用：放段落末尾或独立成行，**不要塞进标题**。
- 标题末尾不加标点。

语气上保留你自己的东西：开场吐槽、夹私货（成绩、排名、心情）、结尾一句情绪。参照：

| 想表达 | 别写 | 写成 |
| --- | --- | --- |
| 自嘲开场 | 经过本人的深入思考，本文将系统性地介绍…… | 这玩意真有大病 |
| 强调结论 | 综上所述，我们可以得到以下结论 | ***连续四个正整数的异或和为 0*** |
| 记录心情 | （直接结束文章） | 😴 |

## 7. 别把写作提示写进正文

建稿脚本会留下这几行提示：

```markdown
<!-- xxx：正文从这里开始…… -->
<!-- 公式：$行内$ 或 $$独立成行$$…… -->
```

**开写后整行删掉**。它们会随 HTML 发布到线上，而且会被算进文章页那句"X 分钟读完"的阅读时长（`readingTime` 统计的是原始 Markdown 正文）。

YAML 注释（`#` 开头）不会发布到线上，可以放心留。

## 8. 发布前自查

1. 标题层级：只有 `h2`/`h3`？没有跳级？没有和 `title` 重复的一级标题？
2. 写作提示注释删干净了？（在 `dist/posts/<slug>/index.html` 里搜 `<!--` 应该搜不到东西）
3. 公式里没有裸中文？页面没有标红的公式？
4. 链接都是 markdown 语法，不是裸 URL？
5. `npm run verify` 绿了？（check + 生产子路径构建 + 产物检查）
